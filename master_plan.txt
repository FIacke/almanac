Установка APK сама по себе НИКОГДА не делает устройство авторизованным.

Доступ выдаётся сервером только после полной цепочки:
  одноразовое приглашение
    → регистрация пользователя
      → регистрация устройства
        → криптографическая привязка
          → серверная сессия
            → проверка прав на КАЖДОМ запросе

При отзыве устройства цепочка обрывается по всей длине:
  REVOKED
    → все активные сессии становятся недействительными
      → все refresh-токены аннулируются
        → все realtime-соединения закрываются
          → все последующие запросы отклоняются

Проверка прав реализуется НА СЕРВЕРЕ, а не в APK. Изменённый APK обходит только
клиентскую логику — но не сервер. Сервер — единственный источник истины.

РАЗДЕЛ 2. АРХИТЕКТУРА ANDROID-ПРИЛОЖЕНИЯ
================================================================================

2.1. Слои (Clean Architecture, упрощённая)

  ui/          — Activity, Fragment, Adapter, кастомные View
  domain/      — бизнес-модели (User, Device, Message, Chat, Group, File) и use cases
  data/
    ├─ remote/   — Retrofit-сервисы, DTO, мапперы DTO↔domain
    ├─ local/    — DataStore (токены, настройки), Room (только кэш UI, не история)
    └─ repository/ — реализация контрактов domain, объединение remote+local
  security/    — шифрование секретов, работа с keystore, проверка отпечатков
  core/        — утилиты, константы, Result-обёртки

2.2. Модели (черновик)

  data class User(val id: String, val displayName: String, val avatarColor: String)
  data class Device(val deviceId: String, val userId: String, val status: DeviceStatus)
  enum class DeviceStatus { ACTIVE, REVOKED, PENDING }
  data class Message(val id, val chatId, val fromUserId, val text, val sentAt, val status)
  data class Chat(val id, val peerUserId, val lastMessage, val unreadCount)
  data class Group(val id, val title, val members: List<Member>, val myRole: Role)
  data class FileRef(val id, val chatId, val url, val mime, val size, val expiresAt)

2.3. Локальное хранилище (минимизация — требование проекта)

  ХРАНИМ:
  ✓ user_id
  ✓ device_id (генерируется один раз при первом запуске, неизменяем)
  ✓ refresh_token (шифрованно, в Android Keystore)
  ✓ access_token (в памяти + шифрованно на диск для восстановления)
  ✓ приватный ключ устройства (в Android Keystore, аппаратное хранилище)
  ✓ настройки UI (тема, звуки, уведомления)

  НЕ ХРАНИМ:
  ✗ историю сообщений (всё на сервере)
  ✗ контакты (получаем с сервера при открытии)
  ✗ файлы (получаем по запросу, кэш только в памяти)
  ✗ пароли в открытом виде (их у нас нет, есть одноразовые коды)

2.4. Шифрование на клиенте

  Android Keystore генерирует пару RSA-4096 (или EC P-256):
  ├─ Приватный ключ НЕ покидает устройство никогда
  ├─ Публичный ключ отправляется на сервер при регистрации устройства
  └─ Сервер использует его для проверки подписи каждого запроса
     (или для шифрования session-key, если решим делать per-message шифрование)

РАЗДЕЛ 4. РЕГИСТРАЦИЯ ПО ОДНОРАЗОВЫМ КОДАМ
================================================================================

4.1. Модель угроз

  Сценарий: кто-то перехватил APK, установил его и пытается зайти.
  Без одноразового кода от администратора он не пройдёт дальше экрана входа.
  Код действует ограниченное время и используется ровно один раз.

4.2. Схема таблицы invites

  CREATE TABLE invites (
      id            UUID PRIMARY KEY,
      code_hash     TEXT NOT NULL,           -- bcrypt/argon2(code)
      created_by    UUID REFERENCES users(id),  -- админ
      created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
      expires_at    TIMESTAMPTZ NOT NULL,
      used_at       TIMESTAMPTZ,             -- NULL = не использован
      used_by_user  UUID REFERENCES users(id),
      assigned_name TEXT,                    -- заготовленное имя пользователя
      status        TEXT NOT NULL DEFAULT 'ACTIVE'  -- ACTIVE | USED | EXPIRED | REVOKED
  );

4.3. Срок жизни и защита

  ├─ Время жизни кода: 15 минут (настраивается)
  ├─ Одноразовое использование: статус → USED атомарно в транзакции
  ├─ Хранение: только ХЕШ кода (argon2id), не сам код
  ├─ Генерация: crypto.randomBytes(8).toString('base64url') → 11 символов
  ├─ Защита от перебора: 
  │    ├─ rate limit 5 попыток / 15 мин / IP
  │    ├─ rate limit 3 попытки / 15 мин / deviceId
  │    └─ логирование всех попыток в audit_log
  └─ При успешном логине: код атомарно помечается USED, устройство привязывается

4.4. Поток регистрации (пошагово)

  Админ → POST /api/admin/invites (Bearer admin JWT)
       ← { inviteId, code }   (code показывается ОДИН раз)

  Пользователь → POST /api/auth/register
       { inviteCode, displayName, devicePublicKey, deviceInfo }
       ← сервер проверяет:
          1. код существует и его хеш совпадает
          2. статус ACTIVE и не истёк
          3. rate limit не превышен
       ← сервер создаёт users + devices + sessions
       ← { userId, deviceId, accessToken, refreshToken }

  Всё в одной транзакции. Если что-то падает — откат (код остаётся ACTIVE).

РАЗДЕЛ 5. ГЛАВНАЯ СИСТЕМА ЗАЩИТЫ УСТРОЙСТВ
================================================================================

5.1. Ключевые сущности

  user_id    — стабильный идентификатор личности (UUID)
  device_id  — UUID, генерируется на клиенте при первом запуске, живёт в Keystore
  device_pub — публичный RSA/EC-ключ устройства (генерируется в Keystore)
  binding    — запись в таблице devices, связывающая user_id ↔ device_id ↔ device_pub

5.2. Схема таблиц

  CREATE TABLE users (
      id            UUID PRIMARY KEY,
      display_name  TEXT NOT NULL,
      role          TEXT NOT NULL DEFAULT 'USER',   -- USER | ADMIN
      created_at    TIMESTAMPTZ DEFAULT NOW(),
      is_blocked    BOOLEAN DEFAULT FALSE
  );

  CREATE TABLE devices (
      id            UUID PRIMARY KEY,           -- = device_id с клиента
      user_id       UUID NOT NULL REFERENCES users(id),
      public_key    TEXT NOT NULL,              -- PEM
      device_info   JSONB,                      -- model, os, app version
      status        TEXT NOT NULL DEFAULT 'ACTIVE',  -- ACTIVE | REVOKED
      registered_at TIMESTAMPTZ DEFAULT NOW(),
      revoked_at    TIMESTAMPTZ,
      revoked_by    UUID REFERENCES users(id),
      last_seen_at  TIMESTAMPTZ
  );

  CREATE TABLE sessions (
      id              UUID PRIMARY KEY,
      device_id       UUID NOT NULL REFERENCES devices(id),
      user_id         UUID NOT NULL REFERENCES users(id),
      access_jti      TEXT,                     -- JWT ID текущего access
      access_expires  TIMESTAMPTZ,
      refresh_hash    TEXT,                     -- argon2(refresh_token)
      refresh_expires TIMESTAMPTZ,
      created_at      TIMESTAMPTZ DEFAULT NOW(),
      revoked_at      TIMESTAMPTZ
  );

5.3. Как выдаются токены

  access_token:
    ├─ JWT, срок 15 минут
    ├─ Payload: { sub: user_id, dev: device_id, sid: session_id, jti, iat, exp }
    └─ Подписан HS256 секретом сервера (позже можно EdDSA)

  refresh_token:
    ├─ 32 случайных байта (base64url), НЕ JWT
    ├─ Срок 30 дней
    ├─ Хранится на сервере в виде хеша (argon2id)
    └─ Обновляется при каждом refresh (rotation), старый инвалидируется

5.4. Проверка КАЖДОГО запроса

  Middleware authRequired:
    1. Взять Bearer access_token
    2. Проверить подпись JWT
    3. Проверить exp
    4. ВЗЯТЬ device_id из payload
    5. SELECT status FROM devices WHERE id = device_id
       → если status != 'ACTIVE' → 401 "device revoked"
    6. SELECT revoked_at FROM sessions WHERE id = sid
       → если не NULL → 401 "session revoked"
    7. (опционально) Проверить подпись запроса публичным ключом устройства

  Это ключевой момент: даже если злоумышленник украл JWT, при отзыве устройства
  следующий же запрос получит отказ.

5.5. Привязка к устройству и защита от подмены device_id

  ├─ При регистрации клиент генерирует пару ключей в Android Keystore
  ├─ device_id = SHA-256(public_key)[:16] — детерминированно
  ├─ Публичный ключ уходит на сервер, приватный — никогда
  ├─ Каждый запрос может подписываться приватным ключом (signature header)
  │  Сервер проверяет подпись публичным ключом из таблицы devices
  └─ Подмена device_id на другой не поможет: подпись не сойдётся

5.6. Что происходит при краже/потере телефона

  Шаг 1. Владелец или админ открывает админ-панель и жмёт "Отозвать устройство"
  Шаг 2. Сервер:
       UPDATE devices SET status='REVOKED', revoked_at=NOW()
       UPDATE sessions SET revoked_at=NOW() WHERE device_id=?
       Отправляет в WebSocket канал устройства команду "kick"
  Шаг 3. Активные WebSocket-соединения закрываются
  Шаг 4. Любой запрос с этим device_id → 401
  Шаг 5. Refresh token больше не принимается
  Шаг 6. На клиенте: при получении 401 "device revoked" — очистить Keystore,
          DataStore, все токены, показать экран "Устройство отозвано"

  Все шаги логируются в audit_log.

5.7. Как сервер отличает разрешённое устройство от неизвестного

  1. Есть ли device_id в таблице devices?           → нет = 401
  2. Статус devices.status == 'ACTIVE'?              → нет = 401
  3. Есть ли активная session для этого device_id?   → нет = 401
  4. access_token не истёк и подпись валидна?        → нет = 401
  5. (опционально) signature запроса совпадает?      → нет = 401

  Только когда все 5 условий выполнены — запрос обрабатывается.

  Все защищённые:
    ✓ JWT подпись и exp
    ✓ device.status == 'ACTIVE'
    ✓ session не отозвана
    ✓ rate limit per device_id

  Админские:
    ✓ всё вышеперечисленное
    ✓ user.role == 'ADMIN'
    ✓ MFA-токен в заголовке X-MFA-Token валиден и не истёк
    ✓ все действия пишутся в audit_log

РАЗДЕЛ 7. БАЗА ДАННЫХ (ТАБЛИЦЫ И СВЯЗИ)
================================================================================

  users           ─┬─ devices        (1:N)
                   ├─ sessions       (1:N, через devices)
                   ├─ chats          (как owner или peer)
                   ├─ group_members  (N:M)
                   ├─ messages       (author)
                   └─ audit_log      (actor)

  devices         ─── sessions       (1:N)
  chats           ─┬─ messages       (1:N)
                   └─ chat_members   (1:N, для групповых)

  groups          ─┬─ group_members  (1:N)
                   └─ messages       (chat_id может ссылаться на groups.id)

  messages        ─── files          (N:M через message_attachments)
  invites         ─── users          (used_by_user)
  audit_log       ─── users          (actor_id)

Ключевые индексы:
  messages(chat_id, sent_at DESC)
  sessions(device_id, revoked_at)
  audit_log(created_at DESC)
  invites(status, expires_at)

РАЗДЕЛ 8. ЛИЧНЫЕ СООБЩЕНИЯ
================================================================================

8.1. Поток отправки

  Клиент → POST /api/chats/:id/messages { text, client_msg_id }
  Сервер:
    1. Проверка авторизации (middleware)
    2. Проверка членства в чате
    3. INSERT INTO messages (id, chat_id, author_id, text, sent_at, client_msg_id)
    4. UPSERT в chat_members последнее прочтение для отправителя
    5. Отправка через WebSocket всем участникам чата (кроме отправителя)
    6. Ответ клиенту: { id, sent_at, status: 'sent' }

8.2. Доставка и прочтение

  WebSocket-события:
    message.new       — новое сообщение
    message.read      — прочитано (chat_id, up_to_msg_id)
    message.delivered — доставлено (msg_id)

  Сервер хранит:
    messages.sent_at       — отправлено
    messages.delivered_at  — последнее подтверждение доставки
    chat_members.last_read — последнее прочитанное сообщение per user

8.3. Синхронизация

  При подключении WebSocket клиент:
    1. Подключается с access_token
    2. Получает список активных чатов
    3. Для каждого чата — последние N сообщений (или с last_seen_message_id)
    4. Подписывается на события

  При разрыве и переподключении — догоняем историю с последнего известного id.

РАЗДЕЛ 9. ГРУППОВЫЕ ЧАТЫ
================================================================================

9.1. Роли

  OWNER   — создатель, может всё, включая удаление группы
  ADMIN   — может добавлять/удалять участников, менять название
  MEMBER  — только читать и писать

9.2. Права (проверяются на сервере)

  Создание       → любой USER
  Добавление     → OWNER, ADMIN
  Удаление       → OWNER, ADMIN (не себя)
  Изменение имени → OWNER, ADMIN
  Закрытие       → OWNER
  Отправка       → все MEMBER+

9.3. Схема

  groups(id, title, created_by, created_at, closed_at)
  group_members(group_id, user_id, role, joined_at, muted_until)
  messages.chat_id → может указывать на groups.id (chat_type = 'group'|'private')

РАЗДЕЛ 10. ФАЙЛЫ (ФОТО, ВИДЕО, ДОКУМЕНТЫ)
================================================================================

10.1. Приватное хранилище

  ├─ MinIO / S3 бакет, НЕ публичный
  ├─ Файл доступен только по временной ссылке (TTL 15 минут)
  ├─ Ссылка выдаётся только после проверки: пользователь — участник чата
  └─ Никаких прямых URL из бакета наружу

10.2. Лимиты

  Фото:   ≤ 15 МБ, jpeg/png/webp
  Видео:  ≤ 100 МБ, mp4/webm
  Файлы:  ≤ 50 МБ, whitelist расширений + проверка MIME
  Число вложений на сообщение: ≤ 10

10.3. Поток загрузки

  1. Клиент → POST /api/files { chat_id, mime, size, name }
  2. Сервер проверяет права + лимиты
  3. Сервер создаёт presigned upload URL (PUT, TTL 15 мин) и запись files (status=pending)
  4. Клиент → PUT прямо в MinIO
  5. Клиент → POST /api/files/:id/confirm
  6. Сервер проверяет, что файл реально загружен (HEAD), меняет status=ready
  7. Клиент отправляет сообщение с attachment_id

РАЗДЕЛ 15. ШИФРОВАНИЕ — КРИТИЧЕСКОЕ РЕШЕНИЕ
================================================================================

15.1. Два варианта, взаимоисключающих

  ВАРИАНТ A — E2EE (полное сквозное шифрование)
    ├─ У каждого пользователя пара ключей X25519
    ├─ При первом контакте — обмен публичными ключами (X3DH)
    ├─ Сообщения шифруются на клиенте (Double Ratchet / Signal protocol)
    ├─ Сервер хранит только зашифрованные блобы
    ├─ Сервер НЕ МОЖЕТ прочитать сообщения
    └─ Админ НЕ МОЖЕТ прочитать сообщения (только удалить/заблокировать)

  ВАРИАНТ B — Управляемое шифрование (сервер знает ключ)
    ├─ TLS для транспорта
    ├─ Сообщения хранятся на сервере в зашифрованном виде
    ├─ Ключ шифрования у сервера
    ├─ Сервер/админ МОЖЕТ прочитать сообщения (по запросу)
    └─ E2EE нет — это "закрытая система", но не "нечитаемая сервером"

15.2. Что выбрать

  Если главная цель — "администратор имеет доступ к содержимому":
    → Вариант B. E2EE несовместимо с этим требованием.
    → Все сообщения шифруются at-rest (диск), но сервер имеет ключ.
    → Админ-панель может показывать переписку.

  Если главная цель — "максимальная защита от сервера":
    → Вариант A. E2EE, сервер только релеи.
    → Админ не может читать, только блокировать.

  ДО РЕАЛИЗАЦИИ КРИПТОГРАФИИ НУЖНО РЕШИТЬ.

15.3. Промежуточный вариант (гибрид)

  ├─ E2EE для всех обычных сообщений
  ├─ Управляемое шифрование для "корпоративных" чатов (по требованию)
  └─ Каждому чату — флаг "encrypted: e2ee|managed"

РАЗДЕЛ 17. BACKUP И RECOVERY
================================================================================

  17.1. Что бэкапим
    ├─ PostgreSQL — pg_dump ежедневно
    ├─ MinIO файлы — rsync ежедневно в другой регион/бакет
    └─ .env и конфиги — в защищённое хранилище (не в git)

  17.2. Как НЕ вернуть отозванное устройство при откате БД

  Проблема: если откатить БД на вчера, отозванное сегодня устройство вернётся
  в статус ACTIVE, и злоумышленник снова получит доступ.

  Решение — монотонная версия состояния:
    ├─ Каждый devices.status_change получает timestamp (revoked_at)
    ├─ Session/session также имеют revoked_at
    ├─ Отдельная таблица revocation_log(id, device_id, revoked_at, reason)
    ├─ При старте сервер читает MAX(revoked_at) из revocation_log
    ├─ Миграция при откате: применить все revocations из revocation_log
    │  на восстановленную БД
    └─ Проще: хранить revocation_log в отдельном append-only хранилище
       (например, тот же Redis с AOF, или отдельная таблица, которую
        бэкапим чаще и отдельно)

  17.3. Тест восстановления
    ├─ Раз в месяц: восстановить БД во временную среду
    ├─ Применить все revocations из лога после даты бэкапа
    ├─ Проверить, что отозванные устройства остаются отозванными
    └─ Если нет — срочно править процедуру

РАЗДЕЛ 20. ПОДПИСАНИЕ APK И БЕЗОПАСНОЕ ХРАНЕНИЕ КЛЮЧА

  20.1. Генерация ключа подписи (один раз)

    $ keytool -genkeypair -v \
        -keystore ~/.android/almanac-release.jks \
        -alias almanac \
        -keyalg RSA -keysize 4096 -validity 10000 \
        -storepass <STRONG_PASSWORD> -keypass <STRONG_PASSWORD>

  20.2. Хранение

    ├─ Keystore НЕ в git (добавить в .gitignore)
    ├─ Пароль — в менеджере паролей (1Password/Bitwarden)
    ├─ Резервная копия — в защищённом хранилище (не в облаке)
    └─ При потере keystore — невозможно обновлять приложение в Play Store

  20.3. Подпись release

    В app/build.gradle.kts:
      signingConfigs {
          create("release") {
              storeFile = file(System.getenv("ALMANAC_KEYSTORE") ?: "almanac.jks")
              storePassword = System.getenv("ALMANAC_STORE_PASSWORD")
              keyAlias = System.getenv("ALMANAC_KEY_ALIAS")
              keyPassword = System.getenv("ALMANAC_KEY_PASSWORD")
          }
      }
      buildTypes {
          release {
              signingConfig = signingConfigs.getByName("release")
              isMinifyEnabled = true
              isShrinkResources = true
          }
      }

    Сборка:
      $ ./gradlew assembleRelease
